# 會員管理系統 ProMax V4.0.0

以本次上傳的 v3.9.2 按鈕排版調整版為基礎。保留會員、消費、10%回饋、店員管理與原有版面。

## 更新方式（既有 v3.9.2）

1. 先備份 Supabase 資料庫，更新期間暫停入帳、關閉舊管理頁。
2. 在既有 Supabase SQL Editor 執行 `sql/10_upgrade_v4_0_0.sql` 全部內容。此檔可重跑，保留會員、交易、點數與客訂。它需要原本 01、04、06、09 的資料結構；08 可已執行或未執行。
3. 不要重跑 `01_setup.sql`，不要刪除資料庫。若缺少 09，先執行 `sql/09_upgrade_v3_9_2_rebuild.sql`，再執行 10。
4. 解壓縮後進入 `line-member-points`，將裡面的全部檔案與資料夾上傳到原 GitHub 儲存庫根目錄；不要只上傳 ZIP，也不要多包一層資料夾。清除舊重複檔案，保留儲存庫。
5. Vercel 保留原專案與環境變數，建置指令 `npm run build`、輸出目錄 `dist`。此包不含可重建的 dist，部署時會自動產生。
6. 部署完成後重新開啟管理端。桌面標題、手機標題與頁尾應顯示 V4.0.0／4.0.0。

從零建置：在全新資料庫依序執行 01、04、06、09、10，再依 02 設定管理員。不要將此順序用於已有資料的資料庫。

## 客訂欄位與操作

- 日期／時間、訂購品名、負責店員、備註。
- 「已付清」勾選＋金額；「已付訂金」勾選＋金額。
- 兩項都可勾選以保留訂金歷史。付清金額是含訂金的總收款，不是尾款，兩個金額不會再相加。
- 勾選時金額須為1至10,000,000元整數；未勾選送出0元。付清總額不得小於訂金。
- 舊資料原本只有「付清」狀態、沒有金額，新版顯示「金額未填」，不擅自補成訂金或0元；編輯時需核對補填。
- 客訂付款紀錄不會自動新增消費或發放點數，正式結帳仍在新增消費操作，避免重複入帳。
- 每筆紀錄只留「編輯、一鍵LINE通知、刪除」；移除下方狀態切換及手動標記通知按鈕。
- 編輯會在同一筆紀錄直接展開完整表單，一次修改全部欄位，不再連續跳出 prompt。
- 刪除會從一般列表隱藏，保留資料與操作紀錄供追查，不影響點數。不會自動退款。
- 客訂中心搜尋在資料庫先篩選再分頁，每頁50筆，不再只搜尋前300筆資料。

## 一鍵LINE通知

本版的一鍵通知是由官方帳號直接發送進度文字，不是跳到店員的個人LINE聊天。按下後會直接處理該筆會員通知，請先確認正在操作正確客人。

首次啟用：

1. 在 LINE 官方帳號啟用 Messaging API，取得該帳號的 Channel access token。
2. 在 Vercel 專案環境變數設定 `LINE_CHANNEL_ACCESS_TOKEN`，套用 Production 後重新部署。憑證只放伺服器，勿放進 GitHub、網頁或聊天室。
3. LINE Login 與 Messaging API 須使用同一個 Provider；會員需透過LINE會員頁登入綁定，並符合官方帳號收訊條件。手動新增且尚未LINE綁定的會員不可直接通知。
4. 管理端「系統設定 → LINE通知」顯示是否填入憑證，並提供官方設定說明與正確的聊天管理連結。已填入不代表憑證有效；實際有效性會在發送時驗證。

缺少憑證會顯示啟用方式，不會假裝已發送。憑證無效、額度不足、會員未綁定與連線中斷都有不同提示。聊天管理連結是 https://chat.line.biz/ ，不會自動選定某個客人；不能用會員 user ID 拼接未經LINE公開支援的聊天室網址。

穩定性：

- 同一筆客訂、同一資料版本沿用資料庫儲存的 LINE retry key、收件人與通知文字；兩位店員同時按或逾時重試，不會另建一個通知內容。
- LINE受理但資料庫紀錄未同步時，可重按同一筆通知完成同步。
- 通知已受理的同一版本不再重複發送；編輯內容後會成為新版本，可重新通知。30秒內的新通知會被限制。
- 結果不明時保留pending紀錄，暫停修改／刪除該筆以免變更通知對象或內容。23小時後停止自動重試，須先在官方帳號核對實際結果，交由管理者處理，不可直接刪除待確認紀錄後重送。
- 介面顯示「LINE已受理通知」，不宣稱已讀或必定送達；被封鎖等情況可能沒有實際送達。
- 本次沒有真實的官方帳號憑證，因此未進行真人發訊，也未替您修改Vercel設定。

官方依據：
- 啟用Messaging API：https://developers.line.biz/en/docs/messaging-api/getting-started/
- 發訊與收件條件：https://developers.line.biz/en/docs/messaging-api/sending-messages/
- 重試鍵與限制：https://developers.line.biz/en/docs/messaging-api/retrying-api-request/
- LINE URL方案：https://developers.line.biz/en/docs/messaging-api/using-line-url-scheme/

## 速度、穩定性與安全修正

- 修正管理頁沒有 #brand／#contact 元素時，共用設定載入程式中斷的根因。設定缺欄位或API回傳null會顯示明確訊息。
- 會員統計在資料庫聚合，單次查詢回傳目前頁面的交易與摘要；不再下載會員所有交易再加總。
- 統計報表與客戶比較使用資料庫原生彙總，保留同期／整月模式；點數流水依操作紀錄計算。
- 客訂寫入、刪除留存與操作紀錄在同一資料庫交易完成。新增有固定UUID；重送不重複新增。
- 多店員修改使用版本檢查，過期表單不能覆蓋新內容。客訂操作不影響會員點數。
- 管理員身分以驗證登入為準；客訂API僅接受允許欄位，不能指定其他操作者或手動偽造通知成功。
- 新函式不授權匿名及一般登入角色直接執行，保留RLS與既有安全Cookie、來源檢查。停用舊客訂寫入RPC的service_role執行權限。
- LINE目標與訊息由資料庫解析，忽略前端傳來的收件人或訊息；通知憑證不回傳前端。
- 會員搜尋保護PostgREST查詢字串；客訂搜尋以文字內容比對，避免特殊字元改變查詢結構。
- 業務備份使用同一資料庫快照，包括付款金額、備註、版本、刪除與通知紀錄。新格式為6，請使用本版還原工具；舊v3/v4備份仍可讀取。還原只允許空的業務表。

## 驗證結果與上線檢查

已通過38項自動測試、新版資料庫整合驗證、既有12項V3資料庫／還原情境，以及DOM互動測試。
測試包含：付款數值、重複提交、跨會員與非管理員阻擋、版本衝突、通知識別碼重用、刪除保留稽核、分頁搜尋、點數不變、備份演練與正式還原、完整表單編輯和三個操作按鈕。

本環境瀏覽器啟動失敗，未完成實際畫面截圖／手機瀏覽器驗證；已做DOM互動及響應式CSS檢查。部署後請：
1. 用手機與桌面各開啟會員列表，確認沒有null錯誤。
2. 用測試會員建立訂金、付清客訂，重新整理確認金額與店員保存。
3. 由另一位店員修改後，用舊表單儲存，確認顯示版本衝突。
4. 設定LINE憑證後，以店內測試帳號驗證一次真實通知及重按不重送。

開發驗證：`npm test`、`npm run build`。`tests/database-v400.mjs`及`tests/database-v3.mjs`需額外@electric-sql/pglite（可用PGLITE_MODULE指定）；`tests/dom-v400.mjs`需happy-dom（可用HAPPY_DOM_MODULE指定）。這些測試套件不需要安裝到正式網站。
